# Subtract chrome, then let agents climb

Hold My Brief's reading surface is already calm. What makes the app feel unpolished is everything around it, and the products it wants to resemble got polished mostly by taking things away. At the default 420x620 window with a PDF open, the app shows **15 interactive controls**, has a **23-item menu that is almost a copy of a 26-command palette**, ships a full library manager that the PRD explicitly deferred, and offers **540 appearance combinations**. Its CSS uses **14 font sizes, 13 radii and roughly 51 padding values** with no tokens for any of them (current UI audit, `src/main.ts:17-41`, `src/style.css`). T3 Code calls itself "a minimal GUI for coding agents" and writes "fight scope creep" into its contributor rules. Linear's 2026 refresh made the sidebar dimmer and used fewer, smaller icons and fewer separators. Readest, a Tauri reader built on the same foliate-js engine, hides its header and footer until the pointer approaches. The changes that would move Hold My Brief furthest are, in order: one visible path per action, a library that stays closed by default, an empty state that is just "Open", the accent colour kept for one role, and a small type, spacing and radius scale. Those changes are safe to make in a loop that a coding agent can run in CI. The loop has a deterministic "floor" (e2e tests, protected screenshots, axe, a check that every action is still reachable) and a "hill" (fewer controls, fewer off-token values, and a pairwise model judge run in both orders). The repo already has most of the pieces in its Playwright config, perf fixtures and reshoot script. A small set of Tauri fixes would make the window feel native: show the window only after the page paints, use the macOS overlay title bar, use native context menus, and keep `:focus-visible` from painting a red ring around the page.

## What the reference apps share: one accent, few sizes, chrome on demand

The reference products differ in stack (T3 Code and Claude Code Desktop are Electron, the Tern apps are Swift or Rust, Readest is Tauri), but they use the same small set of rules. **Chrome appears when you intend to use it.** Readest's 44 px header and 52 px footer fade in over 300 ms only while the pointer is over a trigger strip. An open dropdown keeps the bar visible. The trigger strip was made shorter after it was found covering the first line of text and swallowing long presses on it ([Readest HeaderBar.tsx](https://raw.githubusercontent.com/readest/readest/main/apps/readest-app/src/app/reader/components/HeaderBar.tsx); [FooterBar.tsx](https://raw.githubusercontent.com/readest/readest/main/apps/readest-app/src/app/reader/components/footerbar/FooterBar.tsx)). Readest's default top and bottom page margins equal the header height (44 px), so a revealed bar never covers text ([Readest constants.ts](https://raw.githubusercontent.com/readest/readest/main/apps/readest-app/src/services/constants.ts)). Claude Code Desktop puts a title, a few pane buttons and one ⋮ menu in its title bar. "When the window is narrow, buttons that don't fit move into the menu," and panes without a button "appear in the ⋮ menu once the session has content for them" ([Claude Code Desktop docs](https://code.claude.com/docs/en/desktop)). Zed hides its scrollbar by default ("auto") and turns its minimap off ([Zed default.json](https://raw.githubusercontent.com/zed-industries/zed/main/assets/settings/default.json)). SumatraPDF keeps a sparse toolbar and sends everything else through a Ctrl+K palette. Reviewers note that "there isn't a corresponding UI button for every option" ([SumatraPDF Command Palette docs](https://www.sumatrapdfreader.org/docs/Command-Palette.md); [Dedoimedo review](https://www.dedoimedo.com/computers/sumatra-pdf.html)).

**The accent is a signal, not a theme.** T3 Code is neutral zinc with one blue `primary`, and dark mode is pure black with 8 % white borders ([T3 Code index.css](https://github.com/pingdotgg/t3code/blob/main/apps/web/src/index.css)). The most transferable written source is codingwolf-at/tern's BRAND.md, which describes a small native macOS menu-bar app. It allows "at most one filled Coral element per row, and one Coral-filled button per screen". It rules that semantic colours "never fill a row background", and it deliberately leaves the system accent alone because a global accent "would leak into links, toggles and focus rings" ([tern BRAND.md](https://github.com/codingwolf-at/tern/blob/main/docs/BRAND.md)). Hold My Brief does the opposite. Accent red marks the CTA, the selected library row, the "All references" filter, pressed toggles, focus rings and the scrubber, and two red boxes can be lit in the pill at the same time (audit §3). Note that "Tern" is ambiguous: at least five projects use the name. The most prominent is Stencil's closed-beta terminal, whose design could not be checked. The design evidence here comes from the open-source codingwolf-at and ishaanrajiv repos ([ishaanrajiv/tern](https://github.com/ishaanrajiv/tern)).

**Type and spacing come from a short ladder.** Zed's UI text sizes are 16/14/12/10 px. Its spacing is a 4 px-based scale with compact/default/comfortable variants, and its code says "Always use DynamicSpacing for spacing values" ([Zed typography.rs](https://raw.githubusercontent.com/zed-industries/zed/main/crates/ui/src/styles/typography.rs); [spacing.rs](https://raw.githubusercontent.com/zed-industries/zed/main/crates/ui/src/styles/spacing.rs)). T3 Code names its geometry tokens "so sidebar, palette, tooltip, and toolbar controls cannot quietly drift apart" and adds only two steps below 12 px (11 and 10) for badges and key hints ([T3 Code index.css](https://github.com/pingdotgg/t3code/blob/main/apps/web/src/index.css)). Tern's rule is "at most three sizes per view", with hierarchy coming from weight and colour, not size ([tern BRAND.md](https://github.com/codingwolf-at/tern/blob/main/docs/BRAND.md)). Linear cut theme generation from 98 variables to three LCH inputs: base, accent and contrast ([Linear: How we redesigned the Linear UI](https://linear.app/blog/how-we-redesigned-the-linear-ui)). **Motion is brief and serves a purpose.** Zed uses three durations, 50/150/300 ms, with ease-out-quint ([Zed animation.rs](https://raw.githubusercontent.com/zed-industries/zed/main/crates/ui/src/styles/animation.rs)). Tern caps animations at 200 ms with "no loops, pulses or bounce". Apple's HIG says to "avoid adding motion to UI interactions that occur frequently" ([Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion)). **Copy is short and plain.** T3 Code's empty header is a single muted "No active thread". Tern prefers "Nothing needs you." to celebratory copy and bans exclamation marks and emoji ([NoActiveThreadState.tsx](https://github.com/pingdotgg/t3code/blob/main/apps/web/src/components/NoActiveThreadState.tsx); [tern BRAND.md](https://github.com/codingwolf-at/tern/blob/main/docs/BRAND.md)).

The palettes in the best apps are opinionated, which Hold My Brief's palette is not yet. Zed ranks commands first by recent and frequent palette use, then by fuzzy match with a length penalty, and shows the right-aligned keybinding on each row ([Zed command_palette.rs](https://raw.githubusercontent.com/zed-industries/zed/main/crates/command_palette/src/command_palette.rs)). SumatraPDF 3.6 made the default view commands only, with `@`, `#` and `>` prefixes to switch scope ([Neowin SumatraPDF 3.6](https://www.neowin.net/software/sumatrapdf-36/)). Raycast gives each surface exactly one primary action (↵) and one secondary action (⌘↵). It drops subtitles that repeat the title and asks that either every action has an icon or none does ([Raycast ActionPanel docs](https://raw.githubusercontent.com/raycast/extensions/main/docs/api-reference/user-interface/action-panel.md); [Raycast store guidelines](https://raw.githubusercontent.com/raycast/extensions/main/docs/basics/prepare-an-extension-for-store.md)). Hold My Brief's palette has none of this ranking. With no document open, **20 of its 26 rows are greyed out, and each one repeats "Open a document first"** (`palette.ts:98-110`, screens/03).

Two items stay on purpose. The Delete saved reading data explanation is required by PRD DATA-01, and Rotate is required by FMT-01. Both can move out of the main surfaces into the palette, but neither should be deleted. Some ordering calls involve judgement. There is no telemetry, because PRD DATA-01 forbids hidden telemetry, so "rarely used" is an estimate. And the library, although it is the biggest departure from the PRD, may be a feature the author values. The strongest case against cutting it (#2-3) is that recents-only fails as soon as a user has dozens of briefs. That argues for demoting the library, not deleting it, and the table is written that way.

## A floor-and-hill loop the repo can run today

Hill-climbing UI with an agent works when the "hill" is something the agent cannot game and the "floor" is something it cannot edit. Anthropic's evaluator-optimizer pattern fits this: one call proposes, another evaluates. It needs ground truth from the environment and a maximum iteration count, and it works best "when we have clear evaluation criteria" ([Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Anthropic's eval guidance adds the rest of the structure. Separate capability evals (the hill) from regression evals (near 100 %). Prefer deterministic graders. Isolate trials, because Claude once read git history from earlier trials. And "read the transcripts" ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

**The repo already has most of the harness.** `playwright.config.ts` is sized to 420x620, the e2e specs (29 tests) inject files through `#file-input`, `tests/perf/fixtures.mjs` generates synthetic PDF, EPUB and Markdown files, and `scripts/reshoot-media.mjs` has `loadFile`, `settle` and `shot` helpers plus localStorage seeding for appearance and library state (audit §5). There are no `toHaveScreenshot` baselines yet. One environment blocker needs fixing first: Playwright 1.64.1 wants chromium-1248, but the container has 1243. Passing `executablePath` for the 1243 headless shell works, or the repo can pin Playwright to the installed revision.

The loop below is a concrete design. It lives in `scripts/ui-climb.ts` and runs as a GitHub Actions `workflow_dispatch` job or inside a Claude Code session. Read-only configuration sits in `eval/climb.config.json`: the screen list (the 18 audit states: compact empty, menu, palette, PDF, find, zoomed, library, Markdown, appearance, typography, shortcuts, wide empty, wide PDF with library open and closed, EPUB dark, compact dark), the viewports (420x620, 1080x680), both colour schemes, the protected screens, budgets, judge dimensions and `maxIters`. Each iteration runs these steps.

**Propose.** The agent gets the next item from the ranked table above, the current `metrics.json`, and the last five log entries. It returns one named patch limited to `src/**` and at most N lines. A diff-path check rejects any change to `tests/**`, `e2e/**`, `playwright.config.*`, baselines, `eval/**` or the judge prompt. Editing masks and thresholds is the most obvious way to reward-hack a screenshot gate.

**Floor (all must pass, cheapest first).** Run `tsc` and the vitest suite, then the e2e core flows. Run `toHaveScreenshot` on the protected screens, meaning screens the change is not meant to touch, with a strict `maxDiffPixelRatio`. Playwright already disables animations, hides the caret, and supports `mask` and `stylePath` for volatile regions ([Playwright test-snapshots docs](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/test-snapshots-js.md); [params.md](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/api/params.md)). Then check that axe violations under `wcag2a/aa` with `color-contrast` enabled did not increase, tracking `incomplete` separately ([axe-core API](https://raw.githubusercontent.com/dequelabs/axe-core/develop/doc/API.md)). Check that the set of reachable actions in the ARIA snapshot (directly, or through one palette step) still contains the baseline set. Finally, run the existing `tests/perf/run.mjs --baseline=` and take the median of 5 runs, with a 5 % budget.

**Hill.** Measure computed styles with `page.evaluate` over visible elements. Count unique font sizes, paddings, margins, gaps, radii, shadows and colours, and the share of each that is on-token. Count visible enabled interactive controls per screen (today 15 for PDF and 9 for reflowable files at compact size), accent-coloured elements, and visible text nodes. Measuring computed values rather than source CSS stops an agent from hiding values in inline styles. Then run a pairwise VLM judge, one isolated call per dimension: hierarchy, spacing consistency, clutter, typographic consistency, state clarity, and a "something broke" veto covering overflow, truncation and overlap. Each call is made twice with A and B swapped. A dimension counts only if it wins in both orders, and the judge can answer `tie` or `unknown`. The judge sees only screenshots, never the agent's rationale.

**Keep or revert.** Commit when the floor holds, the metrics are no worse, and the judge favours the candidate on at least one dimension and loses on none. Otherwise run `git reset --hard`. Append the patch, gate results, deltas and verdicts to `eval/runs/<ts>/log.jsonl`. Stop after `maxIters` (about 10) or after K rejections in a row. Open a PR with a before/after strip, which matches T3 Code's rule that "UI changes need before/after images" ([T3 Code AGENTS.md](https://github.com/pingdotgg/t3code/blob/main/AGENTS.md)). A human merges and is the only one who can run `--update-snapshots`.

Two caveats shape the design. First, **model judges are tie-breakers, not objectives.** A study comparing GPT-4o, Claude and Llama with crowdsourced ratings of 30 interfaces found that MLLMs "approximate human preferences on some dimensions but diverge on others" ([MLLM as a UI Judge, arXiv 2510.08783](https://arxiv.org/html/2510.08783v1)). Position bias in pairwise judging is systematic and gets stronger as the quality gap shrinks ([Judging the Judges, arXiv 2406.07791](https://arxiv.org/html/2406.07791v6)), and small gaps are exactly what a hill-climb produces. That is why the swap-and-agree rule and the deterministic metrics carry the weight. Second, **the counters can be gamed by deletion.** An agent can lower "unique sizes" by unstyling things, or lower "controls" by hiding them. The reachable-actions check, the contrast gate, and judging at two viewports in both themes are the countermeasures. Measuring in Chromium is a good proxy for Windows, whose WebView2 is Chromium, and a weaker one for macOS. Add Playwright's `webkit` project for darwin baselines, because Tauri's WebDriver has no macOS support ([Tauri v2 WebDriver docs](https://v2.tauri.app/develop/tests/webdriver/)). Run the inner loop on Linux and the cross-OS matrix only on the final PR. No published reference implementation of this exact loop was found, and the link between these counts and perceived polish is a practitioner heuristic, not a validated one.

## Native feel depends on seven Tauri details the app skips

A read of `src-tauri` for this report shows the window built from JSON with native decorations and no title-bar styling. `setup` sets a default chrome colour and calls `window.show()` immediately (`src-tauri/src/main.rs:695-700`), before the page has applied the saved theme. `theme-boot.js` in `index.html` narrows the gap but does not delay the show. Pinning uses plain `set_always_on_top` (`src-tauri/src/windows.rs:195,212`). Each of the following details closes a visible gap. Readest, a production Tauri reader, solves most of them in commented code.

**Show the window only after the page has painted.** Keep `visible: false`, mirror the saved theme's background in `index.html`, and have the frontend emit a "themed" event after its first frame. Show the window from Rust on that event, with a 1-2 s timeout fallback. That is Readest's exact pattern. If the window-state plugin is used, Readest restores state with `StateFlags::all() & !StateFlags::VISIBLE` because the plugin would otherwise show the window "before the webview has painted its first frame" ([Readest lib.rs](https://raw.githubusercontent.com/readest/readest/main/apps/readest-app/src-tauri/src/lib.rs)). Update `setBackgroundColor` on `onThemeChanged` and on in-app theme changes, so gaps that open during a resize match the theme ([Tauri window.ts](https://raw.githubusercontent.com/tauri-apps/tauri/dev/packages/api/src/window.ts)).

**Merge the title bar into the toolbar on macOS.** Use `titleBarStyle: "Overlay"`, `hiddenTitle: true` and a `trafficLightPosition` that centres the buttons in the toolbar row, with `data-tauri-drag-region` on the bar and on each child that should drag ([Tauri config schema](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-schema-generator/schemas/config.schema.json); [Tauri window customization docs](https://raw.githubusercontent.com/tauri-apps/tauri-docs/v2/src/content/docs/learn/window-customization.mdx)). This removes a whole chrome row from a 620 px-tall window. Two caveats are documented. An Overlay window cannot be dragged while unfocused (tauri#4316), which matters for a pinned reader that people grab without clicking first. And AppKit resets the traffic lights on title changes, resizes, theme changes and fullscreen exit, so Readest re-applies the position in the same main-thread pass and corrects for offsets that differ between macOS 15 and 26 ([Readest traffic_light.rs](https://raw.githubusercontent.com/readest/readest/main/apps/readest-app/src-tauri/src/macos/traffic_light.rs)). On Windows, the native frame is a reasonable choice: with `decorations: false`, snap layouts still do not work because of an upstream WebView2 limitation ([tauri#4531](https://github.com/tauri-apps/tauri/issues/4531)). A small pinned reader rarely needs snap layouts, though, so custom chrome is also acceptable there. If you go undecorated, enable the shadow only on Windows 11, because Windows 10 draws it as a broken three-sided border ([Readest lib.rs](https://raw.githubusercontent.com/readest/readest/main/apps/readest-app/src-tauri/src/lib.rs)).

**Make "pin" mean what users expect on macOS.** Plain `alwaysOnTop` cannot float over another app's fullscreen Space in a built app. The maintainer's answer is that only an `NSPanel` can, through the tauri-nspanel plugin, and panels also do not steal focus ([tauri#9556](https://github.com/tauri-apps/tauri/issues/9556)). For an app whose whole purpose is staying on top, this is arguably the most important native fix. It is also the least verified: the plugin's v2 API was not checked.

**Use native menus for right-click.** Tauri 2's menu API with `PredefinedMenuItem` (Copy, Select All, Separator) gives OS styling, dark mode, keyboard navigation and accessibility for free ([Tauri window menu docs](https://raw.githubusercontent.com/tauri-apps/tauri-docs/v2/src/content/docs/learn/window-menu.mdx)). A native app menu bar (File > Open, View > Zoom, Window > Pin) would also satisfy NAV-01 without any in-window buttons. **Apply web-in-a-window hygiene.** Put `user-select: none; cursor: default` on the chrome only, never on the reading surface. Set `overscroll-behavior: none` on the root, and inside the foliate iframe too, because the parent rule does not reach iframes ([MDN overscroll-behavior](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/css/reference/properties/overscroll-behavior/index.md)). Use a system font stack (`system-ui, -apple-system, "Segoe UI Variable", "Segoe UI"`) at about 13 px for chrome. On Windows, use `scrollBarStyle: "fluentOverlay"` ([Tauri config schema](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-schema-generator/schemas/config.schema.json)). **Skip vibrancy behind the page.** Every window effect requires `transparent: true`, Acrylic and Blur are documented as slow during resize and drag, and transparent windows on Windows have shown a white flash on `show()` ([tauri#15490](https://github.com/tauri-apps/tauri/issues/15490)). A reader's content is an opaque page, so at most use Mica or a macOS `sidebar` material behind the library, or nothing at all. **Lazy-load the engines.** Load pdf.js and foliate-js with dynamic `import()` when a document of that type opens, so first paint ships only the shell. The build is already small (92 kB app JS, 442 kB pdf chunk), so this is a modest gain.

## Conclusion

The most useful finding is that polish here is mostly a matter of removing things, and removals are what a guarded agent loop does most safely. Removing a duplicate control or mapping 14 font sizes onto 6 gives a clear deterministic delta. The reachable-actions check proves nothing was lost, and the judge only has to agree that the screen is calmer. Changes that add something, such as auto-hiding chrome, an NSPanel or an overlay title bar, involve timing, native behaviour and per-OS quirks that screenshots in Chromium cannot see. They should be hand-built and reviewed on real macOS and Windows hardware, not climbed. The practical order is a human-approved first PR covering cuts 1-4 and the token scaffold (item 6), so the metrics have a target vocabulary, then the loop for the long tail of spacing, type and accent cleanup, with the Tauri work running in parallel.

The PRD is the strongest support for all of this. Its intended interface ("a compact title bar with Open, filename, Pin, Lock size, and a menu… a single progress footer") is almost exactly what T3 Code, Tern and Readest converge on. The current UI drifted away from it through additions that were each reasonable on their own. Making the PRD's control list the loop's protected core-task set is the simplest way to keep that drift from coming back.
